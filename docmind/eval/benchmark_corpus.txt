LLM 有两个固有缺陷：

│ ├── prompts.py # RAG Prompt
│ └── chains.py # RAG 链
├── tests/
├── data/ # 上传⽂件存储
├── eval/ # 评估测试集
│ └── questions.json
├── Dockerfile
├── compose.yaml
├──.env
└── requirements.txt

RAG 有⾃⼰独⽴的组件体系（ Loader / Splitter / Embedding / VectorStore / Retriever ），和通⽤
LLM 能⼒（ ChatModel / Agent / Tool ）是不同的关注点。分开后职责更清晰，也符合  LangChain

学习⽬标
掌握混合检索、 Rerank 重排序、 Query 改写等优化⼿段，理解它们解决什么问题。
重要概念解释
1. 纯向量检索的缺陷
向量检索擅⻓语义匹配，但有两个弱点：
专有名词 / 编号搜不准：⽐如 "GB/T 2024-2023" 这种编号，向量可能匹配不到精确字符串
关键词匹配弱：⽤户问 "VPN 怎么配置 " ，如果⽂档中写的是 " 虚拟专⽤⽹络设置 " ，向量能匹配；但如
果是特定产品名 "OpenVPN 2.4" ，向量可能不如关键词精确
2. 混合检索（ Hybrid Search ）
同时做两路检索，然后合并结果：
向量检索：语义相似（解决同义表达）
关键词检索：精确字符串匹配（解决专有名词 / 编号）
PostgreSQL ⾃带全⽂检索（ tsvector  / tsquery ），可以和  pgvector ⼀起⽤：
sql
3. Rerank （重排序）
先粗召回  Top-20 个⽚段，再⽤⼀个更强⼤的  Cross-Encoder 模型对这  20 个⽚段逐⼀打分排序，取
Top-5 。
为什么不直接⽤  Cross-Encoder 检索全库？因为  Cross-Encoder 需要把 " 问题 + ⽂档 " 拼接后⼀起输⼊模
型，计算量很⼤，⽆法对全库做。所以策略是 " 向量快召回  + Cross-Encoder 精排 " 。
常⽤  Rerank 模型： bge-reranker-large 、 Cohere Rerank API 、通义  Rerank 。
4. Query 改写（ Query Transformation ）
⽤户的问题可能表述不清、有指代、太⼝语化。在检索前⽤  LLM 把问题改写成更适合检索的形式：
原问题： " 那个假怎么请？ " → 改写： " 年假的申请流程是什么？ "
-- 向量检索结果
SELECT id FROM document_chunks WHERE user_id=:uid ORDER BY embedding <=>:qvec 
LIMIT 10
-- 关键词检索结果
SELECT id FROM document_chunks WHERE user_id=:uid AND to_tsvector(content) @@ 
plainto_tsquery(:q) LIMIT 10
-- 合并去重，再⽤  RRF 或加权打分排序
